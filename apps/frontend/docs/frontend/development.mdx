This page covers running the frontend locally whilst working on it. Set up the
monorepo and Riven first by following
[CONTRIBUTING.md](https://github.com/rivenmedia/riven-ts/blob/main/CONTRIBUTING.md) -
the frontend needs a running Riven, along with its PostgreSQL and Redis.

## Running the dev server

From the root of the monorepo:

```bash
turbo @repo/frontend#dev
```

This starts three things together:

- the frontend dev server at **https://localhost:9000**
- Riven itself (`@repo/riven#dev`), on `http://localhost:3000`
- GraphQL codegen in watch mode, so types update as you edit queries

The dev server runs over HTTPS with a self-signed certificate, generated into
`apps/frontend/certificates/` on first run. Accept the browser warning the
first time you open it.

The defaults for `ORIGIN` (`https://localhost:9000`) and `BACKEND_URL`
(`http://localhost:3000`) already match this setup, and Riven trusts
`https://localhost:9000` out of the box, so no extra configuration is needed.
Set `RIVEN_SETTING__adminUserCredentials` in `apps/riven/.env.riven` to get an
account to sign in with.

## Environment variables

Next.js loads `apps/frontend/.env.development` (and `.env.local`) in dev. As
well as `ORIGIN` and `BACKEND_URL` from
[Configuration](/docs/frontend/configuration#frontend-container), these are
available:

| Variable                  | Description                                                        | Default |
| ------------------------- | ------------------------------------------------------------------ | ------- |
| `ENABLE_MOCKS`            | Starts an [MSW](https://mswjs.io) server for server-side requests. | `false` |
| `NEXT_PUBLIC_LOG_LEVEL`   | Log verbosity, as a number.                                        | `3`     |
| `NEXT_PUBLIC_LOG_DATE`    | Include timestamps in logs.                                        | `true`  |
| `NEXT_PUBLIC_LOG_COLORS`  | Colour log output.                                                 | `true`  |
| `NEXT_PUBLIC_LOG_COMPACT` | Use compact log output.                                            | `false` |

<Callout type="info">
  `NEXT_PUBLIC_` variables are baked in at build time, so they can't be changed
  on the published Docker image.
</Callout>

## Storybook

Components and pages have Storybook stories, with GraphQL mocked by MSW:

```bash
turbo @repo/frontend#storybook
```

Storybook runs at http://localhost:6006.

## Tests

Run these from `apps/frontend`:

| Command               | Runs                                                    |
| --------------------- | ------------------------------------------------------- |
| `pnpm test`           | Unit tests                                              |
| `pnpm test:component` | Storybook stories as component tests, in a real browser |
| `pnpm e2e:headless`   | Playwright end-to-end tests, against a production build |
| `pnpm e2e`            | Playwright end-to-end tests, in Playwright's UI         |
| `pnpm lint`           | oxlint, with type checking                              |

### End-to-end tests

The end-to-end tests run the real frontend against a mocked backend, so they don't need the backend, a database or Redis. `pnpm e2e:headless` builds the app (through Turborepo, so unchanged builds come from the cache) and tests it with `next start` on port 9100, in every browser. CI does the same, in Chromium only.

`pnpm e2e` opens Playwright's UI against `next dev` on port 9101 instead, for faster iteration. Both run over plain HTTP: `next dev --experimental-https` intermittently drops WebSocket connections, including the HMR socket Next.js uses to send React's debug info for server renders, which leaves pages stuck mid-render.

Import `test` from `#playwright/fixtures.ts`. Its fixtures mock the network with [MSW](https://mswjs.io) handlers, the same as the stories. The handlers answer both the Next.js server's requests, through Next.js' test mode, and the browser's, including GraphQL subscriptions over WebSockets.

- Every test starts from a healthy instance that has already been set up. To change that, override the handlers.
- `test.use({ signedInAs: "admin" })` signs the test in with a role (`"admin"`, `"manager"` or `"user"`). Tests are signed out by default.
- `test.use({ handlers: withHandlers(...) })` adds handlers for every test in a file. `network.use(...)` adds handlers inside a single test. Handlers you add take precedence over the defaults.
- `auth.signIn(role)` is a resolver for the sign-in and sign-up endpoints, for tests that go through the login form.
- `auth.signOut()` is a resolver for the sign-out endpoint, which expires the session cookies.
- `recordOperation(QUERY)` returns the variables of each request for that GraphQL operation, so tests can check what was sent.

Some things to know when writing tests:

- **Shared mock data:** handler factories in `mocks/handlers` (e.g. `home.handler.ts`, `media-details.handler.ts`, `library.handler.ts`) are shared with the stories, so prefer them over new inline mocks.
- **Subscriptions:** a subscription handler only attaches to a WebSocket when the page connects. Add it before the page loads, with `test.use({ handlers })` or `network.use()` in `beforeEach`, rather than in response to something the test does.
- **Cached data:** data fetched in `"use cache"` functions (e.g. the home page's carousels) is cached by the production server across tests. Overriding it in one test won't reliably change what that test sees.
- **Hidden duplicates:** the production build keeps hidden copies of streamed content outside `main`. Scope text queries to `page.getByRole("main")` so they don't match both.

## Building the Docker image

The image is built from the monorepo root:

```bash
docker build -f apps/frontend/Dockerfile -t riven-frontend .
```

Then run it with `ORIGIN` and `BACKEND_URL` set, as in
[Getting Started](/docs/frontend/getting-started).
